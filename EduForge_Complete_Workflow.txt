Part 1: Project Architecture & Directory Structure
============================================================

EduForge is structured as a monorepo containing 4 main components:
1. web: The main public student and instructor portal.
2. admin: The top-level EduForge platform super-admin portal.
3. uni-admin: The dedicated portal for university-level administrators.
4. backend: The Spring Boot Java backend powering all portals.

Part 2: Comprehensive Workflow (Instructor - Student - Admin)
============================================================

EduForge operates seamlessly, transitioning between a standard public environment {"Normal Portal"} and an isolated institutional environment {"University Space"}. Below is the workflow breakdown.

--------------------------------------------------
Section A: The Normal Portal (Public Base Platform)
--------------------------------------------------
This defines the everyday, global functions of the platform.
- Instructors: Once registered, instructors jump straight into a "Waiting Room" pending verification from the general Platform Admin (Tier 1). Upon approval, they unlock the classic studio to construct and publish public courses universally available to the student body globally.
- Students: Regular students can make basic accounts, log in, browse the public platform offerings, track their independent progress loops naturally. They can message general instructors on the site publicly via generic shared tools.

--------------------------------------------------
Section B: Enhancement — The University Space
--------------------------------------------------
EduForge scales higher natively through specific institutional networks titled roughly as the "University Spaces." Students entering registered universities unlock an entirely segmented internal network operating under these structural dynamics:

The Three Tier Structure:
1. Tier 1 — EduForge Platform Admin: Operates the entire system. Focuses on onboarding public Instructors, plus spawning macro University structures (delivering "Join Codes" and logins to the individual Universities).
2. Tier 2 — University Admin Portal: Acts via a distinctly isolated standalone codebase (`uni-admin`). Tier 2 assigns Branches, Sections, maps students mapped, and importantly curates and allocates approved institutional courses cleanly via an internal semester pool.
3. Tier 3 — Instructors and Students: Interact actively via their pre-built default web portals, newly granted localized "University Space" tabs if they registered with corresponding recognized Colleges.

The comprehensive plan for implementing this enhancement phases sequentially:

Phase 1 — University Foundation & Onboarding
- First-Time Binding: If a designated student/instructor logged into their web frontend presses the University module, the system explicitly queries onboard details (University Join Code, Section, GitHub username, Emp Id natively bridging them inward to their university space).
- Mapping matrix: The Tier-2 Admin reviews precisely mapped user records filtered aggressively by Branch/Section arrays.

Phase 2 — University Courses & Semester Allocation
- Dynamic Courses: Instructors design university-tier courses appending precise weightages dynamically mapped (Tests: 30%, Lecture Completion: 10%, Project: 40%). Unlike static generic courses, these are freely edited throughout the instructional cycle.
- Allocation: Instead of automatic publication, Tier 2 Admins now use the dedicated Allocations dashboard to pick APPROVED courses from the faculty pool, map them explicitly to one or more sections, review current allocations grouped by course, remove section allocations when needed, and impose final course completion deadlines.

Phase 3 — Chapter Deadlines, Assessments & Real-Time Marks Engine
- Automated Marks Integration: Built-to-order logic dynamically maps deadline constraints globally into internal grades for both individual branches and pre-set test structures resulting in live dashboarding capabilities per student and detailed cross-matrices per Instructor mapping.

Phase 4 — Live Tests & Synchronous Interactions
- Testing Protocol: Allows faculty to spin up synchronised live assessments (notified immediately and powered by responsive web socket pipelines).
- Broadcast Classrooms: Web-native API integrations leveraging Jitsi allowing ad-hoc real-time broadcasting to enrolled subset branches exclusively.

Phase 5 — Project Space & GitHub Integration
- Teams Setup: The module permits dynamic selective or random group construction. Teams draft concept specs.
- GitHub Integration: Leveraging active endpoints the backend invokes internal Github hooks directly via Instructor keys orchestrating bulk repository generations. The codebase automatically scopes in registered Github users natively attaching explicit students as immediate repository collaborators seamlessly tracing PRs internally within the frontend.

Phase 6 — Final Evaluation, Marks Sheet & Certification
- Rollup Sheets: The platform auto-curates complete metrics based thoroughly upon preset weightages consolidating final evaluation ledgers successfully. Instructors adjust manually pre-submission.
- Certifications: Emits internally verified visual Certificates dynamically post Tier-2 Admin ledger approvals.
